Build plan · durable workflow engine

A conductor for durable, crash-proof workflows.

orqestra runs multi-step workflows that survive process crashes, retry themselves, sleep for days without holding a worker, and fan out across a pool of concurrent workers — the Temporal / Inngest idea, built lean on Postgres and Bun. This is the sequenced plan to get there from the current bare skeleton.

01

The one decision to make first

Your current code leases everything off Redis, but requirement #5 asks for a Postgres-backed queue. That is not a detail — it decides how durability and idempotency work for every feature after it. Settle it now.

Recommendation

Postgres is the system of record. Redis is an accelerator you can add later — never the source of truth.

Every durable fact — run state, step results, queue rows, leases, timers, event subscriptions — lives in Postgres and is mutated inside transactions. Postgres alone can carry the whole engine to production using SELECT … FOR UPDATE SKIP LOCKED as the queue primitive. Reach for Redis only when a specific hot path (rate-limit counters, pub/sub wakeups, concurrency tokens) actually hurts — and keep it as cache/coordination, so a Redis flush never loses work.

Postgres source of truth

  • Transactions give you exactly-once step commits for free — claim, run, persist result in one atomic unit.
  • FOR UPDATE SKIP LOCKED is a correct, contention-free queue with no extra infra.
  • Crash recovery is just "read the rows" — state was never only in memory.
  • Leases, timers, and DLQ are all just indexed columns and timestamps.

Redis optional accelerator

  • Sub-millisecond counters for rate limits (#13) and concurrency tokens (#12).
  • Pub/sub to wake idle workers instantly instead of polling.
  • Ephemeral by nature — a wipe must only cost latency, never a lost run.
  • Introduce it in Phase 6, not Phase 0. Don't couple correctness to it.
02

Invariants the whole engine leans on

Four properties that, if you hold them from day one, make every later feature a small addition instead of a rewrite.

Determinism

Workflow code is replayed on recovery. Completed steps must return their recorded result, not re-run. The function is a plan; the log is the truth.

Idempotency

Every start carries an idempotency key; every step has a stable id. Duplicate triggers and duplicate side effects both collapse to one committed outcome.

Durable-by-default

Nothing exists only in a worker's memory. A step isn't "done" until its result is committed to Postgres in the same tx that advances the run.

At-least-once delivery

Workers can die mid-step, so steps run at-least-once. Idempotency + result memoization turn that into effectively exactly-once.

Leases, not locks

A worker claims work with an expiring lease. Crash → lease expires → another worker reclaims. No job is ever permanently stuck behind a dead worker.

Two run modes, on purpose

Inline run() for tests/local synchronous execution; durable enqueue() for the real queue-backed path. Same definition, two executors.

03

Core data model

The minimal schema that makes durability, queueing, leasing, timers, and history all fall out of the same tables. Everything advanced is a column or an index on top of this.

-- a registered workflow definition + version (versioning matters for long-running runs)
workflow        ( id, name, version, dag jsonb, created_at )

-- one execution of a workflow
run             ( id, workflow_id, status, priority, input jsonb, output jsonb,
                  idempotency_key unique, created_at, started_at, finished_at )

-- the queue AND the durable step log, unified
step            ( id, run_id, name, status, attempt, max_attempts,
                  result jsonb, error jsonb, depends_on text[],
                  run_after timestamptz,        -- sleep / delay / backoff
                  lease_owner, lease_expires_at, -- leasing
                  timeout_ms, priority )

-- things a run is blocked on: an external signal / event
signal_wait     ( id, run_id, event_key, satisfied_at )
event           ( id, key, payload jsonb, received_at )

-- append-only observability spine
history         ( id, run_id, step_id, type, data jsonb, at )   -- timeline + logs
dead_letter     ( id, run_id, reason, snapshot jsonb, at )

-- the claim query every worker runs, in a tx:
SELECT * FROM step
 WHERE status = 'ready' AND run_after <= now()
   AND (lease_expires_at IS NULL OR lease_expires_at < now())
 ORDER BY priority DESC, run_after
 FOR UPDATE SKIP LOCKED LIMIT 1;

That single claim query is the beating heart of the engine — queue (#5), workers (#6), leasing (#7), priorities (#14), delayed/sleep steps (#9), and retry backoff (#4) are all just predicates and columns on it.

04

The roadmap — nine movements

Ordered so each phase produces something runnable and the hardest correctness problems (durability, recovery, leasing) are solved before the fun orchestration features sit on top. Build depth-first: a thin slice working end-to-end beats ten half-features.

Foundation & the pivot

// clean the slate

Restructure the repo, stand up Postgres + migrations, and define the core types. This is where you decide the folder layout you won't fight later, and cut over from redis-only to the Postgres model above.

Durable core (single process)

// correctness before scale

Execute a workflow as a sequence of steps, persisting every step's status and result, and prove you can kill the process mid-run and resume exactly where it stopped. No queue yet — just one executor and the log.

#1 workflow definitions #2 durable step execution #3 crash recovery #8 idempotency
Ships: a workflow that kill -9s halfway and resumes without re-running completed steps.
2

Queue, workers & leasing

// go distributed

Turn the step log into a claimable queue. Run N worker processes that pull work with expiring leases, and add configurable retries with exponential backoff. Now a crashed worker's job is reclaimed, and transient failures self-heal.

#5 run queue (Postgres) #6 concurrent workers #7 leasing + reclaim #4 retries + backoff
Ships: 3 workers draining one queue; kill one mid-step and its lease is reclaimed within the lease TTL.
3

Execution control

// time & kill switches

Steps can now sleep for hours without pinning a worker (just run_after in the future), exceed a timeout and be marked/killed, and whole runs or single executions can be cancelled cooperatively.

#9 sleep / delayed steps #10 step timeouts #11 cancellation
Ships: await ctx.sleep("24h") that releases the worker and wakes on schedule.

Orchestration & DAGs

// the good stuff

Steps run when their dependencies complete; branches fan out to run in parallel and fan back in; results steer conditional paths; and a workflow can spawn and await a child workflow. This is where the depends_on column earns its keep.

#19 step dependencies / DAG #15 fan-out #16 fan-in #17 conditional branching #20 child workflows
Ships: a run that fans out to 10 parallel steps and continues only when all 10 commit.
5

Signals & triggers

// ways in

Runs can pause until an external event arrives, and get started five different ways: a direct API call, an internal event, a cron schedule, a future timestamp, or an inbound webhook. The engine stops being a library you call and becomes a service that reacts.

#18 wait-for-event / signals #21 API triggers #22 event triggers #23 cron / scheduled #24 delayed starts #25 webhook ingestion
Ships: a workflow that blocks on ctx.waitForEvent("payment.confirmed") and resumes when a webhook posts it.
6

Flow control at scale

// backpressure · Redis enters

Protect downstream systems: cap how many of a given step run at once, throttle external calls per minute, and let urgent runs jump the line. This is the natural first home for Redis counters — but the limits stay correct even if you implement them in Postgres first.

#12 concurrency limits #13 rate limiting #14 priorities
Ships: "max 5 Stripe steps concurrently" and "≤100 calls/min" enforced under a 1k-run flood.
7

Failure handling

// when things break for real

Runs that exhaust retries land in a dead-letter queue instead of vanishing; operators can manually retry from there; per-workflow policies decide fail-fast vs continue-on-error; and compensation steps unwind side effects (refund the charge if provisioning fails).

#26 dead-letter queue #27 manual retry #28 failure policies #29 compensation / rollback
Ships: a saga: charge → provision; provision fails → refund runs automatically.

The history table has been filling since Phase 1 — now surface it. A complete per-run timeline, structured logs, duration/queue/retry metrics, full error traces, live worker health, and queue-depth / throughput charts. Plus the UI to drive manual retry (#27) and cancellation (#11).

06

Folder structure to grow into

A layout where each concern has one home, so Phase 6's rate limiter doesn't end up tangled in the executor. Since you're open to a clean pivot, adopt this before Phase 1.

orqestra/
├─ src/
│  ├─ define/          # public API: defineWorkflow, step, sleep, waitForEvent
│  │   ├─ workflow.ts     # the builder → produces a DAG definition
│  │   └─ context.ts      # WorkflowContext handed to step fns
│  ├─ engine/          # the durable brain — no I/O framework here
│  │   ├─ executor.ts     # replay + advance a run one step
│  │   ├─ scheduler.ts    # which steps are ready (deps, run_after)
│  │   ├─ retry.ts        # backoff policy
│  │   └─ compensation.ts # rollback / saga unwind
│  ├─ queue/           # claim / lease / heartbeat
│  │   ├─ claim.ts        # the FOR UPDATE SKIP LOCKED query
│  │   └─ lease.ts
│  ├─ worker/          # the long-running process loop
│  │   └─ worker.ts
│  ├─ store/           # Postgres only — every query lives here
│  │   ├─ migrations/
│  │   └─ repositories.ts
│  ├─ triggers/        # api · cron · webhook · event
│  ├─ control/         # concurrency · rate-limit · priority (Redis optional)
│  ├─ observability/   # history, logger, metrics collectors
│  └─ dashboard/       # the UI + read API (Phase 8)
├─ tests/             # crash-recovery + concurrency tests are first-class
└─ examples/          # the saga, the fan-out, the sleeping workflow

Rule of thumb: engine/ knows nothing about Postgres — it talks to store/ through an interface. That keeps the correctness-critical logic unit-testable without a database, and leaves the door open to swap storage later.

07

Worth stealing from the big engines

Not on your list, but each is cheap to fold in early and painful to retrofit. These are what separate a demo from something you'd actually run.

retrofit-hard

Workflow versioning

A run started on v1 must finish on v1's logic even after you deploy v2 — otherwise long-running or sleeping workflows break on every deploy. Pin the version at start; it's just a column, if you add it now.

correctness

Deterministic replay guard

Detect when replayed workflow code diverges from the recorded history (e.g. someone used Date.now() in a step) and fail loudly instead of corrupting state. Ship a ctx.now() / ctx.random() to make determinism the easy path.

ergonomics

End-to-end typed steps

Infer each step's result type so the next step's input is checked at compile time. It's the single biggest DX win over string-keyed context and it's basically free in TypeScript if designed in from Phase 1.

ops

Namespaces / multi-tenancy

A tenant/namespace column on runs from the start lets you isolate queues, quotas, and dashboards per team later — impossible to bolt on cleanly once data is mixed.

ops

Batch / throttled fan-out

Fan-out of 10k items shouldn't enqueue 10k rows at once. A batched map-step with a concurrency window pairs naturally with the Phase 6 limiter.

safety

Poison-pill detection

A step that crashes the worker process (not just throws) shouldn't infinitely reclaim-and-crash the pool. Count reclaim attempts on the lease and dead-letter after a ceiling.

08

Where this gets hard

The traps that eat the most time. None are blockers — but knowing them now shapes the design so you don't hit them blind.

high

Exactly-once side effects

At-least-once delivery means a step can run twice (worker died after the side effect, before the commit). Design every external call around an idempotency key or a "did I already do this?" check — this is the hardest real-world property and it touches Phase 1 through 7.

high

Replay determinism

If workflow code branches on non-recorded, non-deterministic values, recovery replays a different path than the original run and state diverges. The replay guard and ctx-provided time/random are the fix — but only if they land before people write real workflows.

med

Lease TTL tuning

Too short and healthy long steps get reclaimed and double-run; too long and a crashed worker's job stalls. Answer: heartbeats that extend the lease while a step is genuinely alive, decoupling lease TTL from step duration.

med

Queue fairness under priority

Naive "priority DESC" starves normal runs when high-priority work floods in. Plan for aging or weighted fairness in Phase 6 rather than a raw sort.

med

Timer precision without a hot loop

Sleeps and cron shouldn't mean a tight polling loop hammering Postgres. Use a "next wake" query with a bounded poll interval, or a Redis/pg-notify nudge — decide the mechanism when you build Phase 3.
